2026-06-15 · 18 source modules · ~4k LoC · ~5.6k LoC tests

Five deepening opportunities. The recurring shape: a small, sharp invariant — the account rollup rule, the sync protocol, the valid-handle rule — that has no single seam, so it is re-derived shallow in two or three modules at once. Each candidate names where that behaviour could move behind one interface.

A · Give the account-rollup invariant one home

entrypoints/lib/blocked-merge.ts · entrypoints/lib/blocked-store.ts (mergeRemote) · convex/blocked.ts (recordAction)

Before — invariant copied three ways

mergeBlockedAccount() — action → account

idUnknown: xUserId ? false : …
firstActionAt: min(existing, at)
lastActionAt:  max(existing, at)
blockCount:    +(kind==="block")
status: newer-wins

mergeRemote() — account → account

idUnknown: local && row.idUnknown
firstActionAt: min(local, row)
lastActionAt:  max(local, row)
blockCount:    max(local, row)
status: remoteNewer-wins

recordAction() — action → DB row (Convex)

idUnknown: account && args.idUnknown
firstActionAt: min(account, at)
lastActionAt:  max(account, at)
blockCount:    +(kind==="block")
status: newer-wins

three modules, each re-deriving the same field rules · comments literally say “mirrors …”

After — one deep fold, three thin adapters

merge
Account

merge
Remote

record
Action

foldRollup(base, incoming)

idUnknown · firstAt · lastAt
blockCount · muteCount · status

one interface · one test suite · the rule lives once

Problem

The "one row per account, roll the counts up, learn the id, never duplicate" rule is shallow-copied into three modules; a change to it must land in all three by hand.

Solution

Extract one pure foldRollup over the seven rollup fields; mergeBlockedAccount's existing-branch and mergeRemote both delegate to it.

Wins

  • ▪ locality: the invariant concentrates in one module
  • ▪ leverage: one rule, three call sites
  • ▪ interface is the test surface — one suite, not three mirrors
  • ▪ deletion test passes: arithmetic reappears 3× without it
Two-runtime caveat. The cloud recordAction mirror is pinned only by test today (no ADR forbids sharing). Because blocked-merge.ts is pure — zero chrome / Convex deps — convex/blocked.ts could import the same fold and stop mirroring. Folding Convex onto it is the deepest version, but is Worth exploring separately from the in-process consolidation, which stands alone.
Worth exploring in-process · 1 adapter today

B · Give the cloud-sync protocol a module

entrypoints/popup/main.ts (runCloudSync) · entrypoints/lib/convex-sync.ts · entrypoints/lib/blocked-store.ts

Before — ordering lives in a render function

popup/main.ts renders DOM and sequences sync

  1. 1 store.pending()
  2. 2 sync.pushOutbox(pending) → ids
  3. 3 store.markSynced(ids) ⟂ must follow 2
  4. 4 sync.pullBlocked() → remote
  5. 5 store.mergeRemote(remote) ⟂ must follow 4

two modules, one ordering invariant, no home · the only test path is render → click toggle → flush → assert textContent

After — one interface hides the protocol

popup renders DOM only

const r = await cloudSync.sync()
status.text = r.message

cloudSync.sync()

pending → push → markSynced
→ pull → mergeRemote

ordering invariant, behind one call

tested with a fake adapter — no DOM, no microtask flush

Problem

The five-step push→mark→pull→merge ordering is real domain knowledge with no module; it sits inside a UI render function and is testable only through the popup's DOM.

Solution

A cloudSync module exposing sync(): Promise<SyncOutcome>. The popup renders the outcome; convex-sync.ts stays the I/O adapter behind it.

Wins

  • ▪ locality: ordering invariant gets a home
  • ▪ popup sheds business logic, renders only
  • ▪ interface is the test surface, not the DOM
  • ▪ the deepest internal seam (push order) stops leaking
One adapter today = hypothetical seam. Only the popup calls this. But the second adapter is plausible and partly anticipated: the schema already defines a "background" action source, and ADR-0001's hardening backlog points at unattended sync. A scheduled/background sync would be the second caller that turns this from hypothetical into real — flagged, not assumed.
Strong in-process · small

Problem

The valid-handle regex, the reserved-paths set, and the reply-count clamp are duplicated between content and popup; a fourth lower-cased normalizeHandle drifts in the data layer.

Solution

A small username module owns the rule; content and popup import it. Low effort, clean deletion test.

D · Close the implicit seams between the two surfaces

entrypoints/content/actions.ts (batchState) · rail.ts · quick-block.ts (article.dataset.xbBlocked)

The Reply Rail and Cursor Console coordinate through a mutable export and a shared DOM dataset — two seams with no interface.

Problem

The Reply Rail reads a mutable batchState.running export to suppress collapse, and both surfaces write article.dataset.xbBlocked. Coordination has no named interface, so the coupling is invisible until it breaks.

Solution

A small coordination seam — a batch-status reader and an "acted-on" marker behind named functions — so the two surfaces depend on an interface, not a shared variable and a CSS dataset.

Wins

  • ▪ the seam between bulk & single becomes explicit
  • ▪ locality: coordination rule in one place
Why speculative. The current coupling is small and idiomatic for a content script; this earns its keep only if the two surfaces grow more shared state. Listed so the seam is named, not because it hurts today.
Speculative test seam ≠ caller seam

E · The content script is tested past its interface

entrypoints/content/index.ts (__xblockerTestHooks)

Caller's interface

runContentScript()

+ default export — that's all production sees

Test's interface — a parallel, wider seam

__xblockerTestHooks — 25 re-exported internals

addButtons · blockReplies · blockTweet
blockUserDirectly · checkPageAndAddButton
computeRailY · createDirectBlockRequest
extractUsernameFromTweet · getCookieValue
getMaxReplies · getQuickBlock · getRail
mountQuickBlock · muteReplies · … (+11)

every new tested helper is hand-added here

Problem

Tests cross a hand-maintained 25-entry hooks table that reaches into actions, rail, quick-block internals — a second, wider interface than the one callers use.

Solution

Where a hook just re-exports a pure helper, test that helper through its own module's interface and drop it from the table. The table shrinks to the few genuinely content-script-scoped entries (getRail, getQuickBlock).

Why speculative. Some hooks are unavoidable — the WXT entrypoint wrapper hides the module's internals from a normal import. This trims the table rather than removing it, so the payoff is bounded.

Top recommendation

Start with A — give the account-rollup invariant one home

It is the deepest payoff and the clearest deletion-test win: the same rollup arithmetic is re-derived in three modules, and the codebase's own comments admit it ("mirrors …"). Pulling it behind one foldRollup interface gives the invariant locality and the three call sites leverage — and collapses three parallel "pinned by test" mirrors into one test surface.

Warm up on C (same shape, smaller blast radius) to validate the extraction loop, then take A's in-process consolidation first and decide on the Convex mirror separately.

Execution loop — green before and after

  1. 1 · Characterise current rollup behaviour at foldRollup's would-be interface → green on today's code
  2. 2 · Deepen: route mergeBlockedAccount + mergeRemote through the fold → same tests stay green
  3. 3 · Delete the superseded mirror-arithmetic tests → suite green, behaviour still covered
