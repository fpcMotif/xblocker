Four deepening opportunities. The aim each time is the same: a small interface in front of a lot of behaviour, so the invariant has one home (locality) and one test surface (leverage). The two in-page surfaces — the Reply Rail (bulk) and the Cursor Console (single) — and the Whitelist are named as in CONTEXT.md.

Problem

The "never duplicate a person; roll counts up; learn the numeric id late; fold the old @handle row" invariant is re-implemented in three runtimes — and the code comments admit the mirroring.

Solution

Promote the fold to one pure module (a shared/ import both entrypoints/lib and convex/ pull in). mergeRemote and recordAction call it instead of restating it.

Wins

• locality: the dedup rule lives in one module

• leverage: one fold, three call sites

• interface is the test surface — covered once

• convex/local arithmetic can't drift apart

Deletion test

Delete blocked-merge.ts today and the rollup arithmetic doesn't vanish — it reappears, already, inside mergeRemote and recordAction. That reappearance is the proof the module is load-bearing and the proof its callers are copying it rather than crossing its interface.

Candidate B

Give the Whitelist one deep module

Strong local-substitutable

entrypoints/content/actions.ts (whitelist fns) · entrypoints/popup/main.ts (its own copy) · entrypoints/content/modal.ts

Before — two writers race one storage key

The Whitelist isn't a module — it's smeared across two writers with divergent rules.

After — one module owns the key

Three callers, one seam — add/remove/has/list.

Problem

The popup re-implements the Whitelist: it dedupes with includes() (case-sensitive) and writes chrome.storage directly, bypassing the content script's serialized, case-insensitive mutation chain. Two writers, two rules, one key.

Solution

One whitelist.ts deep module owning normalization, case-folded matching, and the serialized read-modify-write. Popup, content script and modal all call it; nobody touches the raw key.

Wins

• locality: one matching rule, one write path

• closes the popup ↔ content-script race

• kills case-variant duplicate handles

• leverage: tested at one interface, not two

Deletion test

There is nothing to delete — that's the symptom. "The Whitelist" has no single module, so changing how trusted handles are matched means editing actions.ts and popup/main.ts and hoping they still agree. Creating the module concentrates that complexity; today it's spread.

Problem

One file holds the X API, handle parsing, whitelist storage, settings and the bulk-batch engine. Its interface is wide (~25 exports) because there's no single concept — so the content-script test seam (__xblockerTestHooks) has to re-export a dozen internals to reach behaviour.

Solution

Carve the clearest deep module first: the X Action API — caller says blockUser(handle), everything about X's internal endpoint sits behind it. Then peel off the batch engine, handle identity, and settings. rail.ts already imports its engine directly; the rest can follow.

Wins

• interface shrinks; implementations absorb the detail

• X-API knowledge stops leaking to call sites

• tests import modules, not a global hook bag

• index.ts hook surface collapses

ADR-0001 compatible. The inline Cursor Console depends on blockTweet / muteTweet. Carving the X Action API relocates that direct path without changing the technique — the ADR's decision stands.

Lift cloud-sync out of the popup view

Worth exploring mock / test-seam

After — sync behind its own seam

Cloud Backup sync

push outbox → markSynced → pull → mergeRemote

Store + convex-sync are injectable — the contract is the test surface.

Problem

The popup's one piece of real orchestration — drain outbox, mark synced, pull, merge — is a private function inside an 875-line view. To test "sync drains then merges" you must render the whole popup and drive the DOM.

Solution

Move runCloudSync into a cloud-backup.ts module taking the store and convex-sync as its interface. The popup becomes a thin caller; the four-step contract is exercised directly.

Wins

• sync contract becomes the test surface

• locality: push/pull/merge order in one place

• popup view shrinks toward pure rendering

• store + convex are mockable at the seam

Honest caveat

One real caller today (the popup), so this is a hypothetical seam justified mainly by "the interface is the test surface." The second adapter is the test. Weaker than A–C on the two-adapters rule, hence Worth exploring, not Strong.
