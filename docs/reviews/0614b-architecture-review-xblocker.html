Architecture review — XBlocker

2026-06-15 · branch claude/practical-bardeen-124309

XBlocker acts on unwanted X.com replies through two surfaces — the bulk Reply Rail and the single-author Cursor Console — over one direct, session-authenticated block/mute API. The surfaces are well built. The friction is below them: several first-class concepts have no module of their own, so the knowledge that defines them is spread across the callers that happen to need it.

module seam knowledge leak deep module deletion test = remove it; does complexity vanish (pass-through) or reappear across N callers (earns its keep)?

The shape today

entrypoints/content + lib

actions.ts (459 lines, 20+ exports) is a flat grab-bag: the X API, reply-region DOM detection, the Whitelist, the maxReplies setting, and batch orchestration all wear one interface. Every UI module reaches through it — and around it, straight into X's DOM.

Problem. CONTEXT names "the same direct session-authenticated block/mute API" that both surfaces share — but it is functions in a grab-bag, not a module, so its plumbing leaks into the interface.

Solution. One lib/x-session module: blockUser(name) / muteUser(name) → outcome. Live fetch in prod, in-memory fake in tests.

  • ▪ interface shrinks; request-builders go internal
  • ▪ two adapters: live fetch, in-memory fake
  • ▪ locality: X v1.1 quirks in one module
  • ▪ tests stop stubbing global fetch
  • ▪ hardening backlog becomes local change
  • ▪ leverage: one API, both surfaces + batch
Supports ADR-0001. Its "Hardening backlog" — same-origin /i/api URL, capturing the bearer from a live request, sourcing rest_id from the DOM — all land inside this one seam instead of being scattered edits. No conflict; this deepening is the prerequisite the ADR implies.

candidate 04

Lift the surface router out of index.ts; shrink the test-hooks bag

The routing decision (URL → which surface mounts) is private to index.ts. Tests can only touch it via globalThis.__xblockerTestHooks — a 24-entry bag, most of it verbatim re-exports of actions.ts.

After — a router with a real interface

a pure decision; the lifecycle owner applies it
index.ts → thin bootstrap (observe URL, apply route)
hooks bag shrinks to getRail + the few real seams

Problem. The wiring where real bugs live — rail double-mount, Cursor Console torn down on nav, theme-observer leak — has no interface; it is exercised only by exposing internals globally.

Solution. Extract a pure routeFor(url) decision and a small lifecycle owner; index.ts becomes bootstrap, and most of the hooks bag evaporates.

  • ▪ the interface becomes the test surface
  • ▪ route decision tested without the DOM
  • ▪ 24-entry global bag → a handful
  • ▪ locality: mount rules in one module
Caveat. This wiring is covered today (the PL-* suite), and the repo holds a 100% coverage gate — so the win here is a cleaner seam, not new coverage. Sequence it after C1/C2, which carry sharper deletion-test signals.

Top recommendation

01 · Give the Whitelist its own module

Start here. It is the cleanest deletion test on the board — the Whitelist already exists as two divergent copies, so removing the scattered logic doesn't move complexity, it removes a class of it (the popup's chain-less write is a real latent clobber). The two adapters — content and popup — are genuine and already in the tree, so the seam is earned, not hypothetical. It is also the lowest-risk first cut against the 100% coverage gate: pure logic, fakeable storage, a small blast radius. Land it, then take 02 (the X-session API seam) for the larger leverage.

Execution loop — green before and after
  1. Characterise the Whitelist at its target interface → verify: green on today's code
  2. Move the implementation behind lib/whitelist; point both callers at it → verify: same tests stay green
  3. Delete the popup's copy and the superseded shallow tests → verify: suite green, behaviour still covered
